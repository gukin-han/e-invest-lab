# 예외 설계 룰

실패를 어떤 타입으로 표현하고, 어디서 번역할지 정한다.

- 원칙: **예외는 계약의 일부다.** 예외 클래스를 만들지는 "누가 이걸 잡아서 다르게 행동하는가"로 결정한다. 잡는 곳이 없다면 타입도 필요 없다.

## 1. 실패를 세 종류로 나누고, 종류마다 도구를 달리 쓴다

| 종류 | 예 | 도구 |
|---|---|---|
| 예상되는 부재 | 최근 2년 내 사업보고서 없음 | 예외 아님 — `Optional`/결과 타입 |
| 프로그래밍 오류 | null 전달, 잘못된 인자 | 자바 내장 (`IllegalArgumentException` 등) |
| 예상되는 운영 실패 | 외부 시스템 다운, 응답 깨짐 | 도메인 예외 |

- 이유
  - 부재를 반환 타입으로 빼면 예외에는 진짜 실패만 남는다. 예외 계층이 복잡해지는 압력 대부분이 "NotFound류"에서 오는데, 그걸 타입이 흡수한다.
  - 프로그래밍 오류는 복구 대상이 아니라 수정 대상이다. 식별 가능한 타입을 만들 이유가 없다.

## 2. 도메인 예외는 포트 옆에, 도메인당 1개로 시작한다

- 규칙
  - "이 포트는 이렇게 실패할 수 있다"는 계약 조항이므로 domain 패키지에 둔다: `DisclosureSourceException`.
  - 도메인당 1개로 시작하고, 호출자가 실제로 다르게 처리해야 할 구분이 생겼을 때만 세분화한다. 세분화 시점엔 sealed 계층으로 만들어 switch 전수 처리를 컴파일러가 강제하게 할 수 있다.
  - 전역 공용 예외(`BusinessException` + 에러코드 enum)는 쓰지 않는다.
- 이유
  - 포트를 아는 호출자(application)는 어댑터가 아니라 포트의 실패 어휘로 잡는다. 예외가 infra에 있으면 호출자가 infra를 알아야 해서 의존 방향이 깨진다.
  - 전역 공용 예외는 타입 시스템이 도와주길 멈추게 하고(코드 값으로 분기), 에러코드라는 평행 분류 체계를 따로 유지시키며, 모든 도메인을 한 클래스에 결합한다.

## 3. 번역은 어휘가 바뀌는 경계 두 곳에서만 한다

- 규칙
  - infra: 기술 예외(`IOException`, Jackson 등)를 도메인 예외로 **1회** 번역한다. 기술 타입이 포트를 넘지 않는다.
  - interfaces: 전역 핸들러가 도메인 예외를 HTTP 응답으로 번역한다.
  - application은 자기 예외를 만들지 않는다. 다르게 행동할 수 있을 때만(재시도, 부분 실패 집계) 잡고, 나머지는 통과시킨다.
- 이유
  - 계층마다 잡아서 재포장하면 새 정보 없이 클래스와 스택 깊이만 늘고, 모든 중간 계층이 모든 실패 종류를 알아야 하게 된다 — 계층 격리라는 목적을 배반한다.

## 4. checked 예외는 쓰지 않는다

- 이유
  - checked는 시그니처를 타고 모든 중간 계층에 선언·재포장을 강제한다. 번역 지점을 두 곳으로 제한하는 3번 규칙과 양립할 수 없다.

Good (infra에서 1회 번역):
```java
try {
    return objectMapper.readValue(body, DisclosureSearchResponse.class);
} catch (IOException e) {
    throw new DisclosureSourceException("DART 공시검색 응답 파싱 실패", e);
}
```

Bad (계층마다 재포장):
```java
try {
    source.findLatest(corpCode);
} catch (DisclosureSourceException e) {
    throw new ApplicationException(e);   // 새 정보 없는 재포장
}
```
