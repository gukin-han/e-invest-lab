# 문서 작성 규칙

## 1. 문서는 목적별 디렉터리에 둔다

- 규칙
  - 기술 결정 기록: `docs/adr/`
  - 도메인 스펙: `docs/specs/`
  - 컨벤션 및 규칙: `docs/rules/`
- 이유
  - 문서의 위치만 봐도 읽는 목적을 알 수 있다.
  - 결정 기록, 도메인 설명, 작성 규칙이 섞이면 최신화 기준이 흐려진다.

Bad:
```text
docs/
├── architecture.md
├── company-rule.md
└── meeting-note.md
```

Good:
```text
docs/
├── adr/
├── specs/
└── rules/
```

## 2. ADR은 기술 주제별 파일로 기록한다

- 규칙
  - 기술 주제별로 파일을 분리한다.
  - 한 파일 안에 같은 주제의 결정사항을 누적한다.
  - 항목에는 날짜, 상태, 컨텍스트, 결정을 포함한다.
- 이유
  - ADR은 현재 상태만이 아니라 왜 그렇게 결정했는지를 남기는 문서다.
  - 주제별로 누적하면 결정 변경 흐름을 따라가기 쉽다.

Bad:
```md
# 결정 모음

MySQL을 쓴다.
RestClient를 쓴다.
```

Good:
```md
# 외부 HTTP 클라이언트 결정

## 2026-06-06

- 상태: 채택
- 컨텍스트: 외부 API 호출이 필요함
- 결정: Spring RestClient 사용
```

## 3. Specs는 도메인 단위로 작성한다

- 규칙
  - 도메인 단위로 파일을 분리한다.
  - 역할, 책임, 핵심 객체, 인바운드, 아웃바운드를 포함한다.
- 이유
  - 스펙 문서는 코드 구조보다 도메인 경계를 설명해야 한다.
  - 도메인별 입출력과 책임이 분명해야 application, infra 경계도 흔들리지 않는다.

Bad:
```md
# 스펙

회사도 있고 공시도 있다.
```

Good:
```md
# 회사 등록부

- 역할
- 책임
- 핵심 객체
- 인바운드
- 아웃바운드
```

## 4. Rules는 주제별 파일로 분리한다

- 규칙
  - 규칙 문서는 `docs/rules/` 아래에 둔다.
  - 하나의 파일은 하나의 주제를 다룬다.
  - 테스트, 네이밍, 포맷팅처럼 적용 기준이 다른 규칙은 파일을 나눈다.
- 이유
  - 규칙은 코드 리뷰에서 자주 참조되므로 주제별로 찾아야 한다.
  - 한 파일에 모든 규칙이 모이면 수정 충돌과 탐색 비용이 커진다.

Bad:
```text
docs/rules/all.md
```

Good:
```text
docs/rules/testing.md
docs/rules/naming.md
docs/rules/formatting.md
```

## 5. 문체는 개조식과 키워드 중심으로 작성한다

- 규칙
  - 설명문보다 구조와 핵심만 남긴다.
  - 개조식, 키워드 중심으로 작성한다.
  - 인과나 흐름은 `->`로 줄여 표현할 수 있다.
- 이유
  - 문서는 반복해서 읽는 참조 자료다.
  - 긴 설명문은 핵심 기준을 찾기 어렵게 만든다.

Bad:
```md
Java 21의 가상 스레드가 정식 출시되면서, 동기 코드로도
비동기 수준의 처리량을 확보할 수 있게 되었다.
```

Good:
```md
Java 21 가상 스레드: 동기 코드로 비동기 수준 처리량 확보 가능
```

## 6. 이모지와 이모티콘은 사용하지 않는다

- 규칙
  - 문서 본문에는 이모지와 이모티콘을 사용하지 않는다.
  - 헤더, 표, 볼드 강조로 의미를 구분한다.
  - 예외: mermaid 다이어그램 내부처럼 시각 기호 자체가 의미인 경우
- 이유
  - 폰트와 렌더링 환경에 따라 깨지거나 누락될 수 있다.
  - 검색, grep, diff, 코드 리뷰에서 노이즈가 된다.

Bad:
```md
## 좋은 예 [emoji-check]

## 나쁜 예 [emoji-cross]
```

Good:
```md
## 좋은 예

## 피할 패턴
```

## 7. 강조는 볼드와 헤더만 사용한다

- 규칙
  - 강조는 볼드와 헤더만 사용한다.
  - 폰트 색, 이모지, 과한 들여쓰기로 강조를 만들지 않는다.
- 이유
  - 문서 강조 방식이 많아지면 중요한 정보의 우선순위가 흐려진다.
  - Markdown 기본 표현만 쓰면 렌더링 환경 차이를 줄일 수 있다.

Bad:
```md
<span style="color:red">반드시 지킬 것</span>

    매우 중요
        꼭 확인
```

Good:
```md
## 필수 규칙

**반드시 지킬 것**
```
