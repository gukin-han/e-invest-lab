# 커밋 컨벤션

## 1. 커밋 메시지는 tag와 한글 설명으로 작성한다

- 규칙
  - 형식: `tag: 한글 설명`
  - 태그는 영어 소문자로 작성한다.
  - 설명은 한글로 작성한다.
  - 바디는 필요할 때만 작성한다.
- 이유
  - 커밋 목록에서 변경 종류와 내용을 빠르게 구분할 수 있다.
  - 한글 설명은 프로젝트 맥락을 짧고 명확하게 남기기 쉽다.

Bad:
```text
Update test
FEAT: add company
feat: Add company persistence
```

Good:
```text
feat: 회사 등록부 영속화 추가

회사 고유번호 중복을 DB 제약으로 막기 위해 JPA 매핑을 추가한다.
```

## 2. 커밋 태그는 정해진 목록만 사용한다

- 규칙
  - `feat`: 새로운 기능 추가
  - `fix`: 버그 수정
  - `refactor`: 동작 변경 없는 코드 구조 개선
  - `docs`: 문서 추가/수정
  - `test`: 테스트 추가/수정
  - `chore`: 빌드, 설정 등 기타 변경
- 이유
  - 태그 종류가 늘어나면 같은 변경을 사람마다 다르게 분류한다.
  - 제한된 태그 목록은 히스토리 검색과 릴리즈 정리를 쉽게 만든다.

Bad:
```text
style: 테스트 문서 정리
build: Gradle 설정 변경
misc: application.yml 수정
```

Good:
```text
docs: 테스트 문서 정리
chore: Gradle 설정 변경
chore: application.yml 수정
```

## 3. 하나의 커밋은 하나의 작업 단위만 담는다

- 규칙
  - 커밋 제목은 무엇을 했는지 명확히 드러낸다.
  - 서로 다른 목적의 변경은 커밋을 나눈다.
  - 바디에는 필요할 때 왜 그렇게 했는지를 설명한다.
- 이유
  - 작은 작업 단위는 리뷰, revert, cherry-pick이 쉽다.
  - 제목은 변경 요약, 바디는 의사결정 이유를 남기는 역할을 한다.

Bad:
```text
feat: 회사 기능 추가와 테스트 규칙 정리
```

Good:
```text
feat: 회사 등록부 영속화 추가

test: 테스트 네이밍 규칙 정리
```
