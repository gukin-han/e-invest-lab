# 수집기 룰

외부 원천에서 데이터를 가져와 저장하는 유스케이스(수집기)의 공통 구조를 정한다.
company 등록부 동기화, disclosure 사업의 내용 수집, research 리포트 수집 세 곳에서 반복된 패턴을 규칙으로 고정한 것이다.

## 1. 멱등성은 원천의 자연키로 보장한다

- 규칙
  - 원천이 부여한 식별자(corp_code, rcept_no, report_idx)를 unique 제약으로 잡는다.
  - 같은 기간을 다시 수집해도 결과가 같아야 한다 — 재실행이 복구 수단이다.
  - 신규 판별이 필요하면 `existsBy{자연키}` 로 걸러 신규만 저장하고, 전체 덮어쓰기가 맞는 원천(등록부)은 upsert 한다.
- 이유
  - 수집은 실패하고 재시도되는 작업이다. 멱등하지 않으면 재실행이 복구가 아니라 오염이 된다.
  - 우리가 발급한 id 는 실행마다 달라지므로 중복 판별 기준이 될 수 없다. 원천의 자연키만이 "같은 것"을 말한다.

## 2. collectedAt 은 진입점에서 한 번 캡처한 시각이다

- 규칙
  - 트리거(컨트롤러·스케줄러)에서 `clock.instant()` 를 1회 캡처해 아래로 전달한다.
  - 같은 실행에서 저장되는 모든 행은 같은 `collectedAt` 을 가진다.
- 이유
  - 한 실행 = 한 수집 사건이다. 행마다 시각이 다르면 "이 배치가 언제 수집됐나"를 복원할 수 없다.
  - [시간 처리 룰](time-handling.md)의 적용이다.

## 3. 결과는 요약 record 로 반환한다

- 규칙
  - 유스케이스는 `{Behavior}Result` 로 무엇을 얼마나 처리했는지 요약해 반환한다: `(collected, skipped)`, `(upsertedCount)`.
  - 수집한 행 자체를 반환하지 않는다.
- 이유
  - 트리거가 필요한 건 "잘 됐는지"이지 데이터가 아니다. 행을 반환하면 대량 수집에서 메모리와 API 응답이 함께 부푼다.
  - 요약 숫자는 로그·응답·알림 어디에나 그대로 쓰인다.

## 4. 저장 전에 불변식 가드를 통과시킨다

- 규칙
  - 원천 데이터는 저장 직전에 불변식을 검사한다: 길이 상·하한, 필수 구획 존재, 필수 필드 비어있지 않음.
  - 가드 실패는 조용히 저장하지 않고 실패로 처리한다(스킵 집계 또는 예외).
- 이유
  - 원천 서식 변경·파싱 버그는 저장 후에는 정상 데이터와 구분되지 않는다(조용한 오염). 저장 전이 마지막 방어선이다.
  - 검증 방법은 [테스트 룰](testing.md)의 실물 픽스처 회귀·known-violation 규칙과 짝을 이룬다.

## 5. 트리거는 /internal POST 로 시작한다

- 규칙
  - 수집 트리거는 `POST /internal/{자원}/{행위}` 로 노출한다: `POST /internal/analyst-reports/collect`.
  - 기간 같은 인자는 쿼리 파라미터로 받고, 생략 시 기본 창(예: 최근 7일)을 유스케이스가 정한다.
  - 스케줄러가 생겨도 같은 유스케이스를 호출한다 — 트리거만 늘고 로직은 하나다.
- 이유
  - 수동 실행·재수집·디버깅이 첫날부터 필요하다. HTTP 트리거가 가장 싼 운영 도구다.
  - `/internal` 접두사가 외부 API 와 운영 API 를 경로에서 구분한다.

## 6. 외부 원천에는 예의를 지킨다

- 규칙
  - 페이지 순회 사이에 지연을 둔다(예: 1초).
  - User-Agent 를 명시한다.
  - 원천이 정한 페이지 크기·호출 한도를 넘겨 요청하지 않는다.
- 이유
  - 상대 서버 입장에서 수집기는 손님이다. 차단당하면 파이프라인 전체가 죽는다.
  - 지연·식별은 비용이 거의 없고, 차단 리스크는 복구 비용이 크다.
