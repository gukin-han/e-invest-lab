# 주석 룰

주석의 기본값은 0이다. 이름과 구조로 의미가 드러나는 코드를 우선하고, 주석은 그것으로 부족할 때만 더한다.

## 1. 주석을 달기 전에 이름과 구조로 먼저 드러낸다

- 규칙
  - 의미가 모호하면 주석을 붙이기 전에 이름을 바꾼다.
  - 긴 블록에 설명 주석을 달기 전에 메서드로 추출한다.
  - 이름·구조로 표현 가능한 것은 주석으로 대신하지 않는다.
- 이유
  - 주석은 코드와 함께 갱신되지 않아 쉽게 거짓이 된다.
  - 이름과 구조는 컴파일러·도구가 검증하지만 주석은 검증되지 않는다.

Bad:
```java
// 종목코드가 있으면 상장사
if (company.getStockCode() != null) {
}
```

Good:
```java
if (company.isListed()) {
}
```

## 2. "무엇"을 다시 말하는 주석은 달지 않는다

- 규칙
  - 코드가 이미 말하는 동작을 주석으로 반복하지 않는다.
  - getter/setter, 단순 위임, 자명한 호출에 주석을 붙이지 않는다.
- 이유
  - 같은 정보가 두 곳에 있으면 한쪽이 먼저 낡는다.
  - 잡음 주석은 정말 필요한 주석의 신호를 묻는다.

Bad:
```java
// 회사를 저장한다
repository.save(company);
```

Good:
```java
repository.save(company);
```

## 3. 설계 근거와 트레이드오프는 코드가 아니라 docs에 둔다

- 규칙
  - "왜 이 구조로 정했는가" 같은 설계 근거는 코드 주석이 아니라 `docs/adr`·`docs/rules`에 적는다.
  - 클래스·메서드 위에 결정 배경을 장황하게 설명하지 않는다.
- 이유
  - 설계 근거를 코드에 박으면 docs와 중복되고 둘이 따로 낡는다.
  - 근거는 한 곳(docs)에 모여야 결정 변경 흐름을 추적할 수 있다.

Bad:
```java
/**
 * 성공 응답 공통 봉투. 에러는 ProblemDetail 로 별도 처리하므로 여기엔 성공 데이터만 담는다.
 * status code 가 성공/실패를 말하므로 success 플래그를 두지 않는다.
 */
public record ApiResponse<T>(T data) {
}
```

Good:
```java
public record ApiResponse<T>(T data) {
}
```

## 4. 코드로 표현할 수 없는 비자명한 "왜"만 주석으로 남긴다

- 규칙
  - 외부 시스템의 함정, 비직관적 제약, 우회 이유처럼 코드 모양만으로 알 수 없는 사실은 주석으로 남긴다.
  - 주석은 "무엇"이 아니라 "왜"를 적는다.
- 이유
  - 외부 제약은 코드 구조에 드러나지 않아 다음 사람이 같은 함정에 빠진다.
  - 이런 주석은 docs에 둘 만큼 크지 않지만 그 자리에선 꼭 필요하다.

Bad:
```java
String trimmed = raw.trim();
```

Good:
```java
// corpCode.xml 은 미상장사의 stock_code 를 공백 1개로 내려준다 (company.json 은 빈 문자열)
String trimmed = raw.trim();
```

## 5. 불투명한 설정 파일은 주석을 허용한다

- 규칙
  - yml·properties처럼 키 이름만으론 효과를 알기 어려운 설정에는 주석을 허용한다.
  - 단, 그 파일이 이미 쓰는 주석 스타일과 밀도에 맞춘다.
- 이유
  - 설정 키는 코드처럼 이름을 바꿔 의미를 드러낼 수 없다.
  - 활성화 효과가 비자명한 플래그는 주석 한 줄이 탐색 비용을 크게 줄인다.

Good:
```yaml
# 프레임워크 예외(404, 검증 실패 등)도 ProblemDetail 본문으로 내려보낸다
mvc:
  problemdetails:
    enabled: true
```
