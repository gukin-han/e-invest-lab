# 수치 타입 결정 — 원본은 정수, 파생은 BigDecimal, 합계는 원 단위로 내보내지 않는다

## 결정 요약
- **날짜**: 2026-09-27
- **상태**: 채택
- **결과**: 원본 시세 컬럼은 `INT` 유지. 이동평균·수정주가 같은 파생값은 `BigDecimal`. 시가총액 **합계**는 원 단위 JSON 숫자로 내보내지 않는다.

## 컨텍스트

캔들 차트를 위해 `StockPriceResponse` 에 시·고·저·거래량을 추가하면서, 주가가 `int` 인 것이 안전한지 되짚었다. 계기는 "버크셔처럼 주가가 큰 회사는?" 이라는 질문이었다.

## 실측

`daily_stock_prices` 332만 행 전수.

| 항목 | 실측값 | `INT` 최대 대비 |
|---|---|---|
| 최고 종가 | 4,601,000원 | 0.21% |
| 최고 고가 | 4,742,000원 | 0.22% |
| 최고 일 거래량 | 621,065,971 | 28.9% |
| 최고 상장주식수 | 5,969,782,550 | **278% (초과)** |
| 최고 시가총액 (삼성전자 2026-06-18) | 2,119,275,995,400,000 | — |

테이블 크기는 데이터 286MB + 인덱스 280MB.

## 결정 1 — 주가는 `INT` 유지, "전부 BIGINT" 는 기각

`INT` 는 21억원까지 담는다. 실측 최고가가 그 공간의 0.21% 라 466배 여유다.

전 컬럼 `BIGINT` 는 4개 가격 컬럼 × 4바이트 × 332만 행 = **약 53MB (데이터 +18.5%)** 를 내고, 원화 주가가 절대 닿지 않을 헤드룸을 산다. 필요해지면 `ALTER TABLE MODIFY COLUMN` 한 번이고 332만 행 재구축은 몇 분이다. 미리 낼 이유가 없다.

같은 기준이 `volume` 에서는 반대로 답한다. 거래량은 이미 `INT` 공간의 28.9% 를 쓰고 있어 3.5배 급등이면 넘친다 — 동전주 대량 거래일에 실제로 일어날 수 있는 폭이다. 그래서 `BIGINT` 가 맞다.

즉 기준은 타입의 통일이 아니라 **값이 실제로 가질 수 있는 범위**다. 상장주식수는 이미 `INT` 를 278% 초과해 `BIGINT` 가 선택이 아니라 필수다.

### 미국 주식 확장이 바꾸는 것은 크기가 아니다

BRK.A 가 $700,000 이어도 `INT` 범위 안이다. 막히는 건 센트 단위(`700123.45`)라 정수로 표현 자체가 안 되는 것이다. `BIGINT` 로 키워도 해결되지 않는다. 통화별 최소단위 + 환율이 붙는 별도 설계이고, 그때는 컬럼 타입이 아니라 통화 축이 논점이 된다.

원화는 실제로 원 아래 단위가 없다. `INT` 는 이 사실을 정확히 표현한다.

## 결정 2 — 자바 내부를 전부 `BigDecimal` 로 통일하지 않는다

타입이 값의 성질을 드러내야 한다. 원화 주가는 관측된 정수 사실이고, 이동평균은 계산된 실수다. 전부 `BigDecimal` 로 맞추면 **원본과 파생의 구분을 타입이 지운다** — 수집과 통계 후작업을 분리한다는 이 프로젝트의 기본 원칙이 코드에서 안 보이게 된다.

비용 쪽도 근거가 된다. `BigDecimal` 은 내부에 `BigInteger` 를 든 힙 객체라 `int` 4바이트 대비 수십 바이트다. 전 종목 스캔이나 백필처럼 332만 행을 훑는 경로에서 할당 압력이 그대로 늘어난다.

경계 변환 비용이 싸다는 점도 통일할 이유를 약화시킨다. `int` 에서 올라갈 때는 `BigDecimal.valueOf(int)` 가 `long` 으로 넓혀 정확히 변환한다 — `new BigDecimal(double)` 의 고전적 함정을 아예 만나지 않는다. 반대로 통일하면 `equals` 함정(`1000` 과 `1000.00` 은 `equals` 가 false, `compareTo` 만 0)을 전 코드가 지게 된다.

## 결정 3 — 파생값은 `BigDecimal`

이동평균과 수정주가는 정수가 아니다.

- 20일 종가 평균: `276,315.5` 처럼 나온다
- 1:3 액면분할 수정주가: `65,833.33...` — 신세계I&C 1:10 은 나눠떨어졌지만 일반적으로는 아니다

같은 응답 record 안에서 원본은 `int`, 파생은 `BigDecimal` 로 타입이 섞인다. 이건 결함이 아니라 성격이 다르다는 사실을 타입이 드러내는 것이다.

## 결정 4 — 시가총액 합계를 원 단위 JSON 숫자로 내보내지 않는다

가장 좁은 구간이다. MySQL `BIGINT` 는 9.2 × 10^18 까지라 서버는 여유가 100배 넘는다. 문제는 **JSON → JavaScript** 경로다.

```
전 종목 시가총액 합 (2026-06-18) : 7,978,794,576,427,918
Number.MAX_SAFE_INTEGER          : 9,007,199,254,740,991
비율                              : 0.89
```

`node` 실측:

```
현재 합계   safe = true
시장 +12%   safe = true
시장 +20%   safe = false
```

시장이 20% 오르면 이 합계는 브라우저에서 정확히 표현되지 않는다. **예외가 나지 않고 끝자리만 조용히 틀린다.**

대응은 단위 변경이다. 합계를 원이 아니라 **억원 또는 조원 단위 `BigDecimal`** 로 내보내면 크기가 안전 구간 한참 아래로 내려오고 화면 표기와도 맞는다. 화면에는 "7,978조원" 으로 쓸 값이라 원 단위 끝자리를 보는 소비자가 없다.

문자열 전송은 정확하지만 클라이언트가 `BigInt` 나 문자열 산술을 해야 해서 차트에 그대로 못 꽂는다. 기각.

개별 종목 시가총액은 아직 안전하다 — 삼성전자 2,119조원이 한계의 24%. `ShareCountTrendResponse.marketCap` 을 `Long` 으로 내보내는 현재 구조는 유지한다.

## 현 상태

| 대상 | 타입 | 근거 |
|---|---|---|
| `open/high/low/close_price` | `INT` / `int` | 실측 최고가가 공간의 0.21% |
| `volume` | `BIGINT` / `long` | 실측이 이미 `INT` 의 28.9%, 급등 여지 |
| `listed_share_count` | `BIGINT` / `Long` | 실측이 `INT` 초과 |
| `market_cap` (단일 종목) | `BIGINT` / `Long` | JS 안전 정수의 24% |
| 시가총액 합계 | 미구현 | 만들 때 원 단위 숫자 금지 |
| 이동평균 · 수정주가 | 미구현 | `BigDecimal` |

## 재검토 조건

- 미국 주식을 수집하기로 할 때 — 통화 축과 최소단위 설계가 선행되어야 한다
- 시장 전체 합계를 응답에 넣을 때 — 단위를 먼저 정한다
- 개별 종목 시가총액이 JS 안전 정수의 50% 를 넘을 때
