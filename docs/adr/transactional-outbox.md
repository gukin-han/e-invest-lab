# 도메인 이벤트 전달 — 트랜잭셔널 아웃박스 + 폴링 릴레이 채택

## 결정 요약
- **날짜**: 2026-08-17
- **상태**: 채택
- **결과**: `outbox_events` 테이블(V13) + `support.outbox` 모듈. 발행은 도메인 저장 트랜잭션에 합류, 전달은 1분 주기 릴레이가 PENDING 행을 폴링해 핸들러에 위임. 첫 소비자는 EPS 추출 → 슬랙 알림.

## 컨텍스트
- EPS 추출 결과를 슬랙으로 받고 싶다. "추출이 DB 에 저장됨"과 "알림이 나감"이 어긋나면 안 된다 — 저장 없이 알림이 가거나(거짓 알림), 저장됐는데 알림이 안 가는(누락) 상태 둘 다 싫다.
- 슬랙은 외부 HTTP 호출이라 언제든 실패한다. 실패가 추출 트랜잭션을 되감아서도 안 되고, 조용히 사라져서도 안 된다.
- 소비자는 지금 하나(슬랙)지만 발행 측이 소비자를 아는 구조는 이벤트로 나눈 의미가 없다.
- 전달 보장은 **at-least-once** — 중복 알림은 허용, 누락은 불허 (비대칭 비용: 중복은 귀찮음, 누락은 신뢰 상실).

## 트레이드오프

| 관점 | 유스케이스에서 직접 슬랙 호출 | Spring ApplicationEvent (in-memory) | 아웃박스 + 폴링 릴레이 (채택) | 메시지 브로커 (Kafka 등) |
|---|---|---|---|---|
| 저장 ↔ 전달 원자성 | 없음 (커밋 전 호출이면 거짓 알림, 후면 누락 가능) | 없음 (프로세스 죽으면 유실) | **있음** — 이벤트 행이 같은 트랜잭션 | 브로커 발행과 DB 커밋 사이 갭 — 결국 아웃박스가 필요 |
| 외부 실패 격리 | 추출 트랜잭션에 전파 | 리스너 예외가 발행 측으로 전파 | 릴레이 안에서 행 단위 격리 | 브로커가 격리 |
| 재시도 정책 위치 | 어댑터마다 | 없음 | 릴레이 한 곳 (`next_attempt_at` 데이터) | 컨슈머·브로커 설정 |
| 발행 측의 소비자 인지 | 안다 | 모른다 | **모른다** — 행이 계약 | 모른다 |
| 이력·사후 분석 | 로그뿐 | 없음 | 행에 상태·시도 횟수·마지막 오류 | 브로커 리텐션 |
| 운영 의존성 | 없음 | 없음 | **없음** (기존 MySQL) | 브로커 운영 |
| 다중 소비자 | 코드 추가 | 리스너 추가 | 핸들러 추가 (단, 행 하나를 공유 — 아래) | 컨슈머 그룹으로 독립 커서 |

핵심: 원자성과 실패 격리를 둘 다 만족하는 최소 구조가 아웃박스다. 브로커는 다중 소비자의 독립 진행이 필요해질 때의 다음 단계이고, 그때도 발행 측 아웃박스는 남는다.

## 구조 결정
- **`support.outbox` 모듈**: 업무 언어는 없지만 자기 테이블·스케줄을 가지므로 `global` 이 아니라 `support` ([아키텍처 룰 1](../rules/architecture.md)). 도메인과 같은 계층 경계.
- **핸들러 포트 (`OutboxEventHandler`)**: 릴레이는 `supports(eventType)` 로 핸들러를 찾아 위임하고 결과를 행에 마킹한다. 이벤트 타입을 아는 곳은 소비자 도메인뿐 — `EPS_EXTRACTED` 역직렬화는 `research.application.EpsExtractedNotifyHandler` 가 한다. Spring 이벤트로 뿌리지 않은 이유: 리스너 여럿이 행 하나의 성공/실패를 공유하면 "누가 실패했는지"가 데이터에 남지 않는다.
- **재시도는 데이터로**: 실패 시 `attempt_count` 증가 + `next_attempt_at = now + backoff(attempt)`. 백오프 1분 → 5분 → 30분 → 2시간 → 12시간, 6회째 실패는 DEAD + `last_error`. 어댑터는 자체 재시도를 하지 않는다 (재시도 정책이 두 곳에 있으면 곱셈이 된다).
- **행 단위 트랜잭션**: 릴레이는 행마다 결과를 별도 커밋 — 한 건 실패가 나머지를 되감지 않는다.
- **상태 마킹, 삭제 없음**: SENT/DEAD 도 남긴다. 사후 분석·재전송 원료.
- **직렬화 실패의 위치**: 발행 측(`OutboxEventPublisher`) 직렬화 실패는 결정적 코드 버그이므로 잡지 않고 실행을 죽인다 (리포트 단위 FAILED 로 위장하면 버그 하나가 수백 개 FAILED 로 보인다). 소비 측 역직렬화 실패는 행 단위로 격리돼 백오프 → DEAD 로 남는다 (다른 행은 나가야 하므로).

## 유보한 것
- **소비자 둘 이상**: 지금은 행 하나를 모든 핸들러가 공유 — 하나만 실패해도 행 전체가 재시도되어 성공한 쪽에 중복 전달. at-least-once 범위 안이지만, 둘째 소비자가 생기면 소비자별 행(`consumer` 컬럼)으로 쪼개는 게 그 시점의 결정.
- **다중 인스턴스**: 단일 인스턴스라 `SELECT ... FOR UPDATE SKIP LOCKED` 없음. 인스턴스를 늘리면 필요.
- **재추출 재발행**: 파서 업그레이드로 재추출하면 이벤트가 다시 나가 슬랙에 다시 온다. 의도된 동작(새 값이 나온 것)이지만 대량 재추출 전엔 알림을 끄거나 타입을 구분할 것.
